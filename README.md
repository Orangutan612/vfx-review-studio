# 特效评审台 · VFX Review Studio

一个**本地自用**的游戏特效视频评审网站。只做两件事：**评审作品** 和 **给出可执行的修改建议**。
原站（vfxmento.xyz）里的账号、积分、邀请码、公告、优惠活动、历史工单、贴图工坊、复评、QQ 群
等全部去掉，只留主干。

- **零 npm 依赖**：只用 Node 内置模块 + 浏览器原生 API，克隆下来直接 `node server/index.mjs`。
- **视频不出本机**：逐帧解码、接触表、亮度实算全在浏览器里完成，只有抽取出来的截图和数值会发给模型。
- **报告可带走**：一键导出成单文件 HTML（图片全部内嵌）或 Markdown。
- **不配环境也能先看效果**：仓库里带了一份 `demo-report.html` 示例报告，双击就能打开。
- **不用编辑任何文件**：网页上选服务商、粘 API Key、点一下就好，还会当场验证模型能不能读图。

## 一、原站的核心运转逻辑（复刻的依据）

把 vfxmento.xyz 的 `app.js` / `frame-sequence.js` / `report-document.js` 读完之后，它的主干是这样的：

### 1. 不用「跳帧截图」，而是真正逐帧解码

大多数「AI 看视频」的做法是 `video.currentTime = t` 然后截图。这在游戏特效上会出事：
高帧率素材（60/120fps）里，只闪 1/60 秒的爆点峰值帧会被完整跳过，而报告里最值钱的意见
往往就藏在那一帧。

所以原站用 **mp4box 解封装 + WebCodecs `VideoDecoder`** 拿到选区内**每一个**源帧，
再用 `cts/timescale` 的真实显示时间戳做校验（`decoded !== manifest.length` 就直接报错）。
本项目的 `public/frame-sequence.js` 是同一套做法的独立实现。

### 2. 把连续运动压成「接触表」喂给模型

光有孤立的高清截图，模型看不出**运动**；把 450 帧原图全塞进去，又必然爆上下文。
原站的解法是**接触表**：按 **1/30 秒**一格分桶，4 列 × 6 行 = 每页 24 格，
每格画面下方印上 `f123  4.1000s`。一页就能让模型读出这一段的运动，而且格数固定、体积可控。

分桶用的是 `floor(rel × fps + 0.5 − 1e-9)`（就近取整、半格向下）。这不是随手写的：
源时间戳是 `cts/timescale`，`timescale` 不能整除时步长会抖动（30fps + timescale=1000 →
理论步长 33.33 被压成 33/34），用朴素的 `floor(rel × fps)` 每两帧就错一次桶边界。
半格向下是为了让正好压在桶边界的帧归**前**一桶，否则 60fps 源会翻倍成 60 格/秒。

### 3. 逐帧实算两个亮度指标，而不是让模型「感觉」

解码的**同时**，每个像素过一遍：

| 指标 | 定义 | 含义 |
|---|---|---|
| `ba` 亮饱和面积占比 | `V = max(R,G,B) > 190` 且 `S = 255·(1 − min/max) > 70` | 画面里多抢眼 |
| `cw` 白核占比 | `V > 245` | 其中最刺眼的一小撮 |

用 `V = max(R,G,B)` 而不是加权亮度：加权亮度会把纯蓝判成暗，和视觉感受不符。
这两个数覆盖选区内**每一帧**（序列），所以「只闪一帧的白核峰值」测得出来。
报告里的「全片亮度轨迹」就是这条序列画出来的 —— 两条线同时冲高又都远离主形时，
主形就被自己的中层或背景压住了，这是只看几张截图最难发现的一类问题。

### 4. 两段式调用（最关键的设计）

```
接触表(分批) ──► 第一段：只挑时刻，不写建议  ──► 时间点列表
                                                    │
                    按时间点抽原分辨率关键帧 ◄───────┘
                                │
                                ▼
                     第二段：全部证据 ──► 结构化报告 JSON
```

第一段故意**不让模型写建议**，只让它「挑值得放大的时刻」，而且**分批**（每批 ≤24 格接触表），
所以单次请求永远很小、可以并行。第二段才把接触表 + 原尺寸关键帧 + 数值序列一起给它写建议。
这样做的好处：既有连续的全局运动信息，又有局部的高清细节，同时每次请求都不爆。

### 5. 报告是结构化的，不是一段散文

原站的报告字段（`summary` / `suggestions[]` / `p1_hint` / `positive` / `limitations`，
每条建议带 `prio` / `judgment` / `evidenceTime` / `feedback` / `hypothesis` / `actions` /
`expected` / `verify`）直接决定了两件事：建议能**绑定到具体时刻**并配上对应截图，
以及能按 P1/P2/P3 分组、能导出成自包含 HTML。本项目沿用这套结构。

## 二、三步走（完全不用碰命令行）

### 第 1 步 · 装 Node.js（一次性，装过就跳过）

到 https://nodejs.org 下载 **LTS** 版本，一路「下一步」装完。装完不用管它。

### 第 2 步 · 双击启动

打开 `vfx-review` 文件夹，双击：

- **Windows**：`启动.cmd`
- **macOS / Linux**：`启动.sh`（第一次可能要先在终端里执行一次 `chmod +x 启动.sh`）

会弹出一个黑色窗口，并**自动打开浏览器**到 http://127.0.0.1:8787 。

> 这个黑窗口**不要关** —— 它就是服务本身。用完直接关掉窗口，服务就停了。

### 第 3 步 · 粘贴一个 API Key

第一次打开网页时，顶部会有一条黄色提示，点右边的「立即配置」：

1. 「服务商」选 **DeepSeek**（默认就选好了；国内直连、便宜、支持读图）
2. 点提示里的「点这里去申请 →」→ 注册 → 创建一个 API Key → 复制
3. 回到网页，粘到「③ 粘贴 API Key」那一栏
4. 点 **「测试并保存」**

点下去之后，它**会真的发一张红色小图给模型**，确认这个模型确实能读图，然后自动存好、立刻生效 ——
不用重启服务，也不用编辑任何文件。

> 配置存在 `vfx-review/.env`。以后想换一家服务商，随时点右上角「配置模型」。

### 不花钱先看看效果

直接双击 **`demo-report.html`** —— 那是我生成好的一份示例报告，能看到最终产出长什么样。

（进阶：想要完整的交互流程但不调用模型，可以在命令行跑 `node server/index.mjs --mock`，
进入离线演示模式，四步流程完全一样，只是最后用示例报告代替真实评审。）

### 日常用法

1. 拖入一段 MP4 / MOV（≤2 分钟，≤100 MB）
2. 拉选区 —— **只评审选中的这一段**，最长 15 秒（视频超长时界面会拦住你并提示）
3. 右边填作品背景（选填，但写清楚会明显更准），勾选同意发送截图
4. 点「开始评审」，等四步进度走完
5. 报告里每条建议都绑了一个时刻 —— **点时间链接，左上角的视频就会跳到那一刻**，对着看
6. 「下载报告 HTML」得到一个单文件报告（截图全部内嵌，发给别人也能打开）；
   「复制建议为 Markdown」直接把建议贴到群里

## 六、已知边界

- **只支持 MP4 / MOV（H.264 / H.265 / AV1）**。要 WebCodecs 能解的编码；浏览器解不了会明确报错，
  不会静默降级成抽样。
- **选区 15 秒上限**是刻意的。放宽会让接触表页数和 token 一起涨，模型反而看得更差。
  长视频请分段提交。
- 逐帧解码要跑满选区内所有帧。15 秒 60fps ≈ 900 帧，一般机器几秒到几十秒，**不要中途关页面**。
- 建议质量取决于你选的模型。模型说「看不到引擎参数 / 贴图」是正常的 —— 它只看得到画面，
  这一条会被写进报告的「证据边界」里。
- 一次评审约 15–30 张图片进模型，成本自己估。

## 七、与原站的差异

保留：逐帧解码、接触表、亮度序列与轨迹图、两段式取证、结构化报告与优先级分组、单文件导出。

## 八、遇到报错怎么办

### 1.「模型的正文是空的」或「模型的输出被 max_tokens 截断了」

**这是 DeepSeek 的思考模式造成的，不是你的配置错。**

DeepSeek 的思考模式**默认打开**，而且强度默认是 `high`。它会先输出一长段思维链（`reasoning_content`），
**再**写正文，而这两部分**共用同一个 `max_tokens` 预算**。预算不够时，正文就被拦腰切断 ——
典型现象是回复以 `{"summary": "…` 开头、在第一个字段中间断掉。

三个办法，按推荐顺序：

1. **把思考强度降下来**（最快、最省）。编辑 @@BT@@.env@@BT@@：
   @@BT@@LLM_REASONING_EFFORT=low@@BT@@，然后重启服务。
2. **调高输出上限**。编辑 @@BT@@.env@@BT@@：@@BT@@LLM_MAX_OUTPUT_TOKENS=65536@@BT@@（DeepSeek 最大允许 384K）。
   调大**不会**额外收费 —— 只按模型实际生成的字数计费。
3. **把「写几条建议」降一档**（15 条 → 10 条）。

程序本身也会兜底：一旦发现输出被截断，它会**自动把预算加倍重试**，
一直加到你设的上限为止；到顶还截断才会报错，并且报错里会写明上面这三个办法。

### 2.「接口通了，但这个模型似乎读不出图片」

说明该模型确实不支持图片输入。换成多模态模型：@@BT@@deepseek-flash@@BT@@ / @@BT@@qwen-vl-max-latest@@BT@@ / @@BT@@glm-4v-plus@@BT@@。

注意：配置向导的「测试连接」会**真的发一张红色小图**并检查回答里有没有「红色」。
它判定的依据同时包括正文和思维链 —— 所以不会因为思考模式把答案写在思维链里而误报。

### 3.「模型没有返回任何内容」

正文和思维链都是空的。一般是**模型名填错**了，或者这家服务不支持这种请求格式。
报错里会带 @@BT@@finish_reason@@BT@@ 便于排查。

### 4. 又慢又贵

也是思考模式的代价。它让建议质量更高，但每次评审都要先「想」一遍。
觉得不划算就把 @@BT@@LLM_REASONING_EFFORT=low@@BT@@。

另外注意：**取证阶段是按接触表分批调用模型的**（每批最多 24 页接触表）。
选区越长，批数越多、调用次数越多。15 秒的选区大约 19 页 ≈ 1 批；
如果发现慢，优先缩短选区，而不是降档位。

### 5. 改了 @@BT@@.env@@BT@@ 要做两件事

- 改 @@BT@@LLM_API_KEY@@BT@@ / @@BT@@LLM_BASE_URL@@BT@@ / @@BT@@LLM_MODEL@@BT@@：**点「测试并保存」，立即生效**，不用重启。
- 改 @@BT@@LLM_REASONING_EFFORT@@BT@@ / @@BT@@LLM_MAX_OUTPUT_TOKENS@@BT@@：**要重启服务**（关掉黑窗口再双击 @@BT@@启动.cmd@@BT@@）。

## 九、评判标准到底基于什么

### 现在是三样东西叠出来的

1. **模型的预训练审美**（占比最大，也最不可控）—— `deepseek-flash` 在训练时见过大量影视与游戏美术，
   它对「什么算好特效」有一套隐式直觉。这部分你改不了。
2. **写死的《特效评审准则》**（`server/review.mjs` 里的 `RUBRIC`）—— 8 个维度，
   每个维度几条**能指着画面回答是 / 否**的判据。它约束「按什么标准评」。
3. **浏览器逐像素实算的数值** —— 亮饱和 ba、白核 cw、运动强度 mo，以及由它们推出的空档、爆点、收尾。
   它约束「拿什么当依据」。

### 它**不会**学习

必须说清楚：这套工具**没有记忆、没有微调、没有检索库**。每次评审都是独立的 ——
不会因为你上次纠正它就改变，不会积累，也不会自己去爬魔法盒。
同一条视频、同样的设置，两次评审的建议会有细微差别。

### 那魔法盒这类作品库能拿来当标准吗

**不能直接拿。** 我实际翻过它的首页、参考栏目和高赞作品评论区：

- 首页是**作品流 + 点赞数**。高赞是「结果」，不是「准则」——
  一万个人说「牛逼」不会告诉你「第 4.7 秒白核面积占了六成，所以主形被吃掉」。
- 高赞作品的 102 条评论我逐条看过，**几乎全是社交吹捧**（「帅」「神了」「牛逼」），
  没有一条是成文的评审意见。
- 「参考」栏目是 392 页分类图片（火焰 / 冰水 / 魔法 / 雷电 / 手绘…），是**灵感库**，不是判据。
- 而且图片本身提取不出文字标准 —— 从作品反推准则这件事必须由人来做。

### 所以真正做的是：准则显式写死 + 给模糊维度配客观数据

**① 8 个维度逐条核对**（报告里的「评审准则核对」表）

| 维度 | 判据举例（都能指着画面回答是 / 否） |
|---|---|
| 主形可读性 | 缩到 10% 还能认出形状吗？爆点最亮那帧主形边界还在吗？ |
| 明度结构 | 最亮的地方是不是眼睛该看的地方？转灰度后前中后景还分得清吗？ |
| 节奏与分段 | 四个阶段能分辨吗？有空档吗？爆点是全段最强吗？ |
| 运动连贯性 | 拖尾连续还是断裂？各层方向打架吗？有抽帧感吗？ |
| 色彩关系 | 主辅色关系成立吗？灰度下层次还在吗？ |
| 材质与细节 | 是不是「先做形体、再加光」？远景下糊成一团吗？ |
| 收尾与循环 | 消散彻底吗？有孤立亮点残留吗？循环能接上吗？ |
| 制作的可靠性 | 大面积半透明叠加导致发灰吗？亮部过曝丢细节吗？ |

每个维度模型必须给 `pass / warn / fail / unknown` + 依据时刻 + 看到的画面。
**漏填的会被程序补成 `unknown` 并标出来**，赖不掉。

**② 新增「运动强度 mo」给节奏撑腰**

亮度只能说明「亮不亮」，说明不了「动不动」。所以这一版在逐帧解码时顺手多算了一个
`mo`（与上一帧的平均灰度差），**不额外解码、不额外上传**。由它自动推出：

- **空档**：连续 mo 低于峰值 12% 且超过 0.25 秒的区间 —— 观感上就是「画面停住了」
- **爆点**：mo 的峰值时刻
- **收尾**：最后 0.5 秒 mo 相对峰值的比例 —— 判断「收得干脆」还是「拖着不散」

这些数字直接写进交给模型的证据里。所以「节奏拖沓」不再是一句感觉，
而是「9.20–9.75s 的 mo 只有峰值的 8%」这种可以核对的话。

### 更进一步：用真素材做对比

准则解决「按什么标准评」，但**没有一个具体的对照物**，标准仍然是抽象的。
如果你手上有真正优秀的参考片段，见第十章 —— 那才是把「直觉」换成「对比」的办法。

### 想换成你自己的标准

直接改 `server/review.mjs` 里的 `RUBRIC` 数组：加维度、删维度、改判据都行，
报告和提示词会自动跟着变。这是整份评审标准**唯一**的出处。

## 十、参考库：用真素材做对比

### 为什么必须有它

模型的预训练直觉**不能**替代真正的对比。原因很具体：

- **不可归因** —— 它说「这里感觉不够好」，你追问「哪里不如谁」，它答不上来。
- **不可复现** —— 同一条视频两次评审，措辞会飘。
- **是平均值** —— 训练语料里混着大量平庸作品，「直觉」是这些东西的平均倾向。
- **没见过实机** —— 已上市游戏的特效主要活在视频与直播里，语料占比极低。
- **我看不到它见过什么** —— 训练数据没公开，模型自己也说不准。所以「它见过大量优秀作品」这句话本身就是推测，不是事实。

而一个真人导师的价值，恰恰在于他能说「你这不如《XX》那一招，因为……」。
这句话要成立，**必须有一个具体的 XX**。

### 怎么用

1. 把参考视频丢进 `reference/` 文件夹，或在网页「参考库」里点「＋ 添加参考视频」。
2. 勾选要参与对比的（最多 3 个）。
3. 正常跑评审。参考会被**用和你作品完全相同的管线**解码，一起交给模型。

### 关键设计：为什么参考也要走同一套管线

**模型看不了视频。** 你给它一个 mp4，它还是看不了 —— 这一点必须先接受。

所以参考素材要先经历和你作品一模一样的处理：

```
mp4 / mov ──mp4box 解封装──► WebCodecs 逐帧解码 ──► 接触表 + 运动强度序列
```

这样对比才是公平的：**你的接触表 vs 标杆的接触表**。
如果只是「让模型知道有个优秀作品」，它就只能回到凭印象 —— 那绕了一圈又回到原点了。

### 模型被要求怎么对比

提示词里写死了纪律：

- 必须说清「标杆在某一刻怎么处理、你的作品在某一刻怎么处理、差在哪」
- **不许**写「建议多参考优秀作品」这种等于没说的话
- 标杆没有解决某个问题就直说，**不许为了用上参考而硬凑**

结果落在报告的「标杆对比」区块里。程序还会做一道校验：
**标杆名必须对得上你真实提供的文件名**，对不上的一律丢弃 ——
免得模型顺手编一个不存在的「参考作品」，那比没有参考更糟。

### 关于魔法盒这类作品库

我**没有**把魔法盒的内容扒进工具里。技术上做得到（它的播放地址是阿里云 PrismPlayer 动态加载的），
但我不做，两个原因：版权与 ToS 不合适；把别人的内容打包进你的程序也不是你想要的。

顺带纠正我前面的一处错误：我上次说「评论区全是社交吹捧」，那是只翻了一篇就得出的结论。
你给的那篇（星溯）评论区里就有一条**具体、可执行、作者本人认可**的意见：

> **逆袭**：好看的，后面爆发展示的后期抖动去掉会不会更好一些呢
> **小新卖蜡笔**（作者）：确实后面震屏弱化一下好些，但是想的是不能完全没有，谢谢大佬指点

正确答案是：这类社区里**偶尔**有真意见，但密度很低、格式散乱，没法直接当准则用。
真正的路子还是你自己收集素材，丢进 `reference/`。


### 四种添加参考的方式

1. **录屏捕获**（最通用）—— 点「● 录屏捕获」，选中正在播视频的那个标签页，录 3 秒即可。
   它直接按 1/30 秒采样、现场拼接触表，**不经过「下载成文件」这一步**，所以对任何网站都有效。
2. **本地上传** —— 点「＋ 本地上传」选文件。你自己录好的、有授权的都行。
3. **直接丢进文件夹** —— 把文件放进 `reference/`，刷新页面。
4. **从链接添加** —— 粘一个链接。
   - 是视频**直链**（`.mp4` / `.mov`）→ 直接下载；
   - 是**播放页** → 工具会读页面自己声明的地址（`og:video` / `<video src>` / `<source src>` / JSON-LD `contentUrl`）；
   - 页面里没有地址（JS 动态生成 / 带访问控制）→ 会明确让你改用「录屏捕获」。

### 为什么魔法盒的作品不能直接粘链接

这不是「能不能扒」的问题，是**那根本不是一条直链**。

我扒了魔法盒的接口（`/works/ajaxdetail`），它返回的是这个：

```
vid      : '8061948fc2a371f18530e7f6c5490102'
playauth : 'eyJTZWN1cml0eVRva2VuIjoiQ0FJUzFBTjFxNkZ0NUIyeWZTaklyNXZQR012WDNxWkV3cXJU…'
```

`playauth` 是**阿里云视频点播的签名安全令牌**（解码开头的 `eyJTZWN1cml0eVRva2Vu` 就是 `{"SecurityToken"`），短期有效。要拿到真正的视频流，得拿这个 token 去调阿里云的 `GetPlayInfo` 接口换地址。

这和「下载一个公开的 mp4」是两回事 —— 它是在**拆掉对方播放器专门设计的访问控制**。这件事我不做，跟版不版权无关。

**所以正确做法是用「录屏捕获」** —— 它不依赖拿到文件，录的是你自己的屏幕。
选中正在播这个视频的标签页，录 3 秒，它就直接变成可对比的参考了。

```
小技巧：录屏时只录你真正想学的那一段。参考片段只取前 3 秒参与对比（控制 token），
所以把想学的那一招放在开头。
```

### 并排对照（左=你的作品，右=参考）

报告里每条建议下面会有一块 **「对照组」**：

- **左半边**：你作品在这一刻的画面
- **右半边**：模型从你的参考库里挑出的**最适合拿来对比的那一刻**

挑不出来就留空，**不会硬凑** —— 程序还会校验参考名必须对得上真实存在的文件，
对不上的整条丢掉（否则报告里会冒出一个不存在的「参考作品」，那比没有更糟）。

为什么要专门做这件事：光有文字结论，读者看不到「标杆长什么样」，对比就落不了地。
参考样片是在解码接触表的**同一遍**里顺手抽出来的，不额外解一次视频。

### 静态参考图（最多 15 张）

参考库不只收视频，也收 **PNG / JPG / WebP / GIF**：概念图、别人作品里的一帧、你自己画的草图都行。

- 单张上限 12 MB，最多 **15 张**
- 静态图不需要解码，直接缩放成一张「接触表」送进模型
- 视频仍然是最多同时选 3 个

### 录屏捕获怎么用

1. 点「● 录屏捕获」→ 浏览器弹出选择框，**选中正在播参考视频的那个标签页**
2. 右下角出现控制面板，但**还没开始录** —— 先切到参考页面找到你想学的那一刻
3. 点面板上的 **「开始录制」**，然后让它播
4. 想让它跟着你走，点 **「弹成悬浮窗」** —— 它会变成一个始终浮在最前面的独立小窗口
5. 看够了在面板上点 **「停止并保存」**（中途可以暂停）
6. 参考立刻出现在列表里并自动高亮（自动起名，想改在列表里点「重命名」）

几个说明：

- **为什么非要「弹成悬浮窗」**：面板原本画在我们这个标签页里，你一去看参考页面它就被盖住了 ——
  这是网页的硬限制，一个页面没法在别的标签页上作画。悬浮窗是独立窗口，才能浮在上面。
- **切走了还在录吗**：在。取帧用的是 `MediaStreamTrackProcessor`（由媒体管线驱动），
  不是 `requestAnimationFrame`（那个在后台标签页会被节流甚至暂停，录出来是死帧）。
- **面板可以拖着走**，位置会记住。
- **每次都要手动选共享目标**：这是浏览器的隐私设计，绕不过去。
- **最长 30 秒**，到顶自动停。中途可以暂停。
- **录屏参考只在当前页面有效**，刷新就没了。想长期保留就自己另存一份再「本地上传」。

### 报告里会附上参考示例图

参考片段不会只变成一句文字结论 —— 报告里会**把它们本身的接触表也画出来**，
和你作品的截图并排，方便直接对照。这正是原站报告里「静态 / 动态案例参考」那一块的作用。

参考片段同样经过「逐帧解码 → 接触表」处理，所以两边的呈现方式是一致的，看图就能比。

### 支持的格式

只支持 **MP4 / MOV** —— 逐帧解码走 mp4box，webm / mkv 解不了。单个文件不超过 100 MB，每个参考只取前 3 秒参与对比（控制 token）。

## 十二、分享给朋友（GitHub）

### 为什么 GitHub 合适

因为这个项目**零依赖、纯本地**：朋友下载下来双击就能跑，代码在仓库里，数据在他们各自电脑上。

| 东西 | 在哪 |
|---|---|
| 程序代码 | GitHub 仓库 |
| API Key | 朋友自己的 `.env` —— **不在仓库里** |
| 参考素材 | 朋友自己的 `reference/` —— **不在仓库里** |
| 评审报告 | 朋友自己的浏览器 / 下载目录 |

各人的 Key 各人付钱，谁也看不到谁的。

### 第一次传上去

```bash
cd D:\Software\DeepSeek_Harness\vfx-review
git init
git add .
git status              # ← 关键一步：确认列表里没有 .env
git commit -m "first commit"
git branch -M main
git remote add origin https://github.com/你的用户名/仓库名.git
git push -u origin main
```

> ⚠️ **`git add .` 之后一定要先 `git status` 看一眼。**
> `.gitignore` 已经排除了 `.env` 和 `reference/`，但那是你的 API Key ——
> 值得多花三秒钟确认。一旦推上去，GitHub 的机器人几秒内就会扫到并盗用你的额度。

### 朋友怎么用（完全不用命令行）

1. 到你仓库点 **Code → Download ZIP**
2. 解压到任意位置（不用装 Git）
3. 装 Node.js LTS（一次性）
4. 双击 `启动.cmd`
5. 网页上点「配置模型」，粘**他自己**的 API Key

### ⚠️ 万一不小心把 Key 提交上去了

**先作废，再清理。顺序不能反。**

1. 立刻去 DeepSeek 控制台**删掉那个 API Key**，新建一个
2. 再改 `.env`、再清理 Git 历史

为什么顺序不能反：GitHub 有机器人在扫新提交的密钥，**几秒内**就会拿去跑。
而 Git 历史里的东西删不干净（即使你 force push，别人 fork 的副本、GitHub 的缓存里可能还有）。
**作废是唯一真正有效的止损**，清理历史只是补救。

### 你怎么发新版

1. 改代码
2. 把 `package.json` 里的 `"version"` 加一点（`1.0.0` → `1.1.0`）
3. 提交并推上去：

```bash
git add .
git commit -m "新功能：xxx"
git tag v1.1.0
git push && git push --tags
```

4. 在 GitHub 上把这个 tag 发成 **Release**（朋友那边会显示得更清楚）

### 朋友怎么知道有新版

1. 在他们的 `.env` 里加一行：`UPDATE_REPO=你的用户名/仓库名`
2. 网页右上角会显示版本号（形如 `v1.0.0`），**点一下**就去 GitHub 问有没有新版
3. 有新版会给出下载入口

**它不会自动替换文件** —— 自动替换等于把代码往别人磁盘上写，出错就是把人家的东西搞坏。所以只提示，动作交给用户。

更新时提醒朋友：**保留 `.env` 和 `reference/`**，只替换代码文件。

### 想真正「实时」更新？

让懂一点技术的朋友直接用 Git：

```bash
git clone https://github.com/你的用户名/仓库名.git
cd 仓库名
git pull          # 想更新时跑这一句
```

`git pull` 才是真正的实时更新。ZIP 下载那条路适合完全不懂技术的人。
